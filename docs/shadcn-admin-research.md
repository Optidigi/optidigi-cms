# Optidigi shadcn admin research

## Recommendation

Make `/admin` a shadcn-only Next.js application for editors and platform operators in the existing app. Keep Payload as the data, authorization, publishing, and MCP backend. Move each workflow behind a small server-only Optidigi interface. Keep the current production admin serving until its replacement meets the cutover checks below. This proposal changes no database schema, provider, or production routing on its own.

The Next.js App Router supports separate root layouts through route groups. Give the new admin its own layout and CSS entry, so it does not inherit Payload admin providers, styles, form state, router, or import map. Preserve REST, GraphQL, media delivery, and MCP routes because they also serve other clients. Keep the configured admin and login paths aligned with flows that use them for redirects. Verify custom routes and API mounts on the built standalone image. [Next.js route groups](https://nextjs.org/docs/app/api-reference/file-conventions/route-groups), [Payload admin routing](https://github.com/payloadcms/payload/blob/v4.0.0-beta.10/docs/admin/overview.mdx), [Payload Next.js auth exports](https://github.com/payloadcms/payload/blob/v4.0.0-beta.10/packages/next/src/exports/auth.ts)

## UI composition

- Shell: shadcn Sidebar, Breadcrumb, Command, and responsive Sheet. Add the active site selector, account controls, editor navigation, and permission-aware operator navigation. Use the official dashboard block as a component reference. The site workspace shows current editorial work and actions such as edit homepage, recent drafts, and open site. [Sidebar](https://ui.shadcn.com/docs/components/base/sidebar), [dashboard blocks](https://ui.shadcn.com/blocks/dashboard)
- Content lists: Data Table, filters, pagination, Empty, and Dropdown Menu. Put tenant scope, filter allowlists, sort, and pagination on the server. Build editable screens with Field, Input, Select, Tabs, and Alert Dialog, and use Resizable panels for the actual Astro preview. Use a single shadcn component family consistently. Generate or copy only the audited components we need and commit them to source. [Data Table](https://ui.shadcn.com/docs/components/base/data-table), [Field](https://ui.shadcn.com/docs/components/base/field), [Resizable](https://ui.shadcn.com/docs/components/base/resizable), [shadcn introduction](https://ui.shadcn.com/docs)
- Rich text: shadcn supplies visual primitives. Preserve the existing Lexical JSON format for content already stored. If the custom UI needs full rich text, use Lexical as an editor engine with shadcn controls and test round trips of existing nodes, relationships, and uploads. The homepage pilot can start with the structured fields Astro consumes. [Payload v4 rich text](https://github.com/payloadcms/payload/blob/v4.0.0-beta.10/docs/rich-text/overview.mdx)
- Assistant: use the current shadcn AI Elements Chat, Message Scroller, Prompt Input, Tool, and Confirmation patterns. Keep website and saved document context visible. Show verified results such as draft saved with editor and preview links, explicit delete approval, and reply stop. Model configuration remains tenant BYOK and uses the existing write-only credential flow. Use the official chatbot as a UI reference and retain the existing provider and endpoint contracts. [AI Elements](https://ui.shadcn.com/docs/ai-elements), [chatbot template](https://github.com/shadcn-ui/chatbot-template)

## Server contracts and behavior

| Area | Public integration and checks |
|---|---|
| Sessions | Reuse Payload sessions and configured secure cookies. Use documented Next auth helpers for login, logout, and refresh when appropriate, and authenticate from the actual request headers. Validate return URLs against intended same-origin destinations. Enforce authentication and authorization in every Server Action and Route Handler. Apply origin protections to browser mutations. Return only UI-specific fields from server-only modules. [Payload server functions](https://payloadcms.com/docs/local-api/server-functions), [Next.js data security](https://nextjs.org/docs/app/guides/data-security) |
| Tenants | Use the active website ID as a requested scope. Verify membership or the applicable platform privilege on the server, then constrain queries and mutations to the active site. Pass the authenticated Payload request with `overrideAccess: false` on user-driven operations. Validate foreign IDs and uploads against the same scope, including relationships and direct URL access. Preserve collection and field access controls and hooks. [Tagged Local API](https://github.com/payloadcms/payload/blob/v4.0.0-beta.10/docs/local-api/overview.mdx), [multi-tenant plugin](https://github.com/payloadcms/payload/blob/v4.0.0-beta.10/docs/plugins/multi-tenant.mdx) |
| Editing | Use domain operations such as `listPages`, `getPageForEdit`, `saveDraft`, `publishPage`, and `restoreVersion`. Use explicit draft, status, and locale semantics. Keep admin language separate from content locale. Implement autosave feedback, stale-write protection, and conflict behavior for concurrent editors, and verify that autosave never publishes. Design and test concurrency at the write boundary. A UI-only dirty flag cannot enforce it. [Tagged drafts](https://github.com/payloadcms/payload/blob/v4.0.0-beta.10/docs/versions/drafts.mdx), [version history](https://github.com/payloadcms/payload/blob/v4.0.0-beta.10/docs/versions/overview.mdx), [v4 migration guide](https://github.com/payloadcms/payload/blob/v4.0.0-beta.10/docs/migration-guide/v4.mdx) |
| Preview and media | Reuse the existing tenant-bound preview grant and Astro preview route. Refresh the iframe after a successful draft save from the custom editor, checking origin and message source if using postMessage. Keep draft data out of shared caches and preserve Astro framing protection. Keep upload validation and transformations in Payload. Confirm the separately deployed site only reads published content and updates without a redeploy. [Payload server-side preview](https://github.com/payloadcms/payload/blob/v4.0.0-beta.10/docs/live-preview/server.mdx), [upload configuration](https://github.com/payloadcms/payload/blob/v4.0.0-beta.10/docs/upload/overview.mdx) |
| Assistant stream | The existing endpoint produces custom text, approval, and error SSE events. First adapt them to the shadcn presentation. If adopting AI SDK `useChat`, either map that protocol in a supported transport or use AI SDK UI message streams for structured events. Validate tool result cards against real server outcomes and never replay mutations automatically after a stream disconnect. Preserve server-validated, single-use delete approval. [AI SDK transport](https://ai-sdk.dev/docs/ai-sdk-ui/transport), [stream protocols](https://ai-sdk.dev/docs/ai-sdk-ui/stream-protocol) |

## MCP consent cutover

The pinned MCP plugin defaults to built-in OAuth and registers `/admin/mcp/authorize` as a Payload view. Its consent data is sealed and decoded by private plugin code. The public token hooks customize issuance, refresh, and authentication. There is no documented headless consent renderer or reader in this beta. A shadcn screen should not ask the user to approve an opaque client without showing the verified client identity and destination. [Tagged MCP OAuth docs](https://github.com/payloadcms/payload/blob/v4.0.0-beta.10/docs/plugins/mcp.mdx#oauth), [view registration](https://github.com/payloadcms/payload/blob/v4.0.0-beta.10/packages/plugin-mcp/src/index.ts), [consent view](https://github.com/payloadcms/payload/blob/v4.0.0-beta.10/packages/plugin-mcp/src/views/Authorize/index.tsx)

Keep the existing flow during development. For final removal of all Payload-rendered screens, either use an upstream public headless consent contract if a later supported version provides one, or configure the documented external MCP authorization server and map validated bearer tokens to current Payload users. The external route is an architecture decision because the issuer supplies the consent UI and must support the MCP clients in use. That is separate from customer model provider keys. If preserving current built-in OAuth is required at cutover, retain its consent screen as an explicit exception until a supported replacement is proven. Test allow, deny, expiry, callback, refresh, and actual tenant-scoped tool calls. [External OAuth integration](https://github.com/payloadcms/payload/blob/v4.0.0-beta.10/docs/plugins/mcp.mdx#sign-in-with-an-external-authorization-server), [OAuth endpoint implementation](https://github.com/payloadcms/payload/blob/v4.0.0-beta.10/packages/plugin-mcp/src/endpoint/oauthServer.ts)

## Automatic stable updates

The existing CI builds and publishes a tested image, checks migration and integration tests on fresh Postgres, and checks candidate container readiness. It does not currently verify upgrades against existing data or promote to production automatically.

1. Once stable v4 is adopted, use a dependency bot to group Payload and all installed `@payloadcms/*` packages on the same exact stable patch or minor. Exclude major releases and prereleases from automatic promotion. Keep the shadcn component source and runtime dependency updates reviewable separately. [Renovate automerge](https://docs.renovatebot.com/key-concepts/automerge/)
2. CI tests the candidate against fresh Postgres and a disposable, access-controlled restored production snapshot or scrubbed representative copy with matching schema and migration history. Detect schema changes without checked-in migrations. Keep production credentials and customer model keys out of this environment. Use a deterministic provider fixture for streamed chat and approvals. [Payload migrations](https://github.com/payloadcms/payload/blob/v4.0.0-beta.10/docs/database/migrations.mdx)
3. Require actual workflow tests against the candidate image. Check sign-in and logout, two-tenant isolation across reads, writes, files and tools, Dutch and English draft and publish behavior, version restore, real Astro preview, and external MCP consent. Check the previous image against the migrated schema before relying on an image rollback. Stable v3 release history includes both regressions and documented security migrations, so a version range is insufficient evidence on its own. [Stable patch regression](https://github.com/payloadcms/payload/issues/16031), [stable migration requirements](https://github.com/payloadcms/payload/releases/tag/v3.90.0)
4. Automatically promote the tested digest when the gates pass and the migration falls within the tested recovery policy. Serialize production deploys, verify readiness and a post-cutover smoke test, and roll back compatible releases by digest on failure. Hold updates with failed tests, destructive or incompatible migrations, or unresolved release steps. Avoid an unattended database restore after editors have written new content. Off-host production backup implementation remains a separate task. [Compose startup ordering](https://docs.docker.com/compose/how-tos/startup-order/), [GHCR pull by digest](https://docs.github.com/en/packages/working-with-a-github-packages-registry/working-with-the-container-registry#pulling-container-images)

## Build order and acceptance

1. Build the isolated shadcn shell, signed-in and signed-out routes, tenant switcher, and server contract. Prove two-tenant access with the backend before layering on more screens.
2. Finish one real homepage workflow: edit NL and EN, save draft, preview the customer site, publish a selected locale, and verify the public page updates. Include conflict and permission tests.
3. Mount the assistant beside the document. Prove tenant BYOK, message streaming, a confirmed draft result with a preview link, and delete approval. Then fill out the remaining content, media, site settings, user and tenant administration, recovery, and account workflows.
4. Preserve old document URLs through compatible routing or redirects. Verify MCP consent, production-like deployment, and rollback. Switch `/admin` when the workflows in use have replacements. Remove Payload admin imports from the new UI and add a lint boundary to prevent them from returning. Enable stable auto-promotion after the upgrade gates have run successfully.

Research only. Compatibility conclusions are based on installed package and tagged source inspection. No implementation or runtime cutover was tested in this pass.
